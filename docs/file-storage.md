# Supabase Storage for property files and profile images

Set `SUPABASE_URL` and `SUPABASE_SECRET_KEY` only in the NestJS environment. Existing projects may instead use the legacy `SUPABASE_SERVICE_ROLE_KEY`. Do not put either privileged key in Vite. Set `SUPABASE_STORAGE_BUCKET` (default `property-files`) and `SUPABASE_PROFILE_BUCKET` (default `profile-images`), then run `npm run storage:setup` once. This command creates missing private buckets and verifies existing ones. It fails if an existing bucket differs, so an operator can review production settings before changing them. Both buckets have a **5,000,000-byte per-file limit**. The property bucket accepts JPEG, PNG, WebP, and PDF; the profile bucket accepts JPEG, PNG, and WebP.

The NestJS API checks the account role and property ownership before it creates a signed upload URL. Owners can upload to their unapproved properties; administrators can upload to any property. The browser sends file bytes directly to Supabase using that URL, then calls the completion endpoint. The API downloads the pending object, checks its actual size and magic bytes against the declared type, and moves it to a final key before marking its PostgreSQL file record ready. The move prevents a still-valid upload URL for the pending key from replacing the displayed object. Property and file IDs never grant access by themselves: download URLs are issued only after another property access check and expire after 60 seconds.

Property managers can read their assigned properties and files. Only administrators can assign a manager, set review status, or access every property. Owners can update unapproved records. Files remain private. Published Stay listings receive short-lived signed URLs for their property's cover photo; draft and rejected listings are not publicly readable.

Profile images use the same signed direct-upload and completion pattern. The API verifies actual bytes, moves a completed image to a final object key, updates the user's profile, then removes the previous object. A failed replacement leaves the previous profile image in place. Only the signed-in user can read, replace, or remove their profile image.

Uploads set a 60-second browser cache lifetime. Signed download tokens expire after 60 seconds, but CDN cache lifetime is separate: a previously fetched response may remain available from cache after token expiry, and object deletion invalidation can take up to 60 seconds. New profile-image URLs use a new object key. Do not treat token expiry as an immediate revocation of already fetched bytes. See [Supabase's CDN guidance](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

Before an upload becomes visible, the API checks its bytes, size, signature, and (when configured) streams it to a private-network ClamAV daemon using `INSTREAM`. Set `CLAMAV_HOST` and optionally `CLAMAV_PORT` (default 3310). `FILE_SCAN_REQUIRED=true` enforces scanning in non-production environments; production enforces it automatically. A missing or unreachable scanner prevents new uploads from becoming ready. Pending files remain private while awaiting a successful scan. ClamAV's TCP socket has no built-in authentication or encryption, so keep it on a trusted private network or use a secure tunnel. See the [ClamD protocol guide](https://docs.clamav.net/manual/Usage/ClamdProtocol.html).

The scanner connection has a 15-second absolute deadline and accepts only a complete clean response. Infected files fail completion; scanner errors and disconnects leave the upload pending for a later retry. File completion and expired-upload cleanup lock the same database upload record and recheck its state. Parent-record locks serialize cover-photo and profile-image replacements. Property and evidence completion can safely retry a READY record. Profile completion consumes its pending record; after a lost completion response, fetch the current profile image before preparing another upload.

Run `npm run storage:cleanup` from a trusted scheduler every six hours to remove expired pending property files, inspection and maintenance evidence, and profile images. `npm run storage:cleanup -- --dry-run` previews the count. Cleanup uses bounded batches and rechecks expiry while holding a database row lock; a completed upload is preserved. Deletion starts after 2 hours 5 minutes, allowing a five-minute grace beyond the upload lifetime for delayed signed-URL issuance. Use `--prefix pending/test-run/` to restrict a check to isolated test objects. Final-file retention periods are an operational policy decision; this command never removes ready files. Keep final objects private and do not publish signed URLs in logs.

For live acceptance after a backend build, run `node --env-file=.env scripts/acceptance-check.cjs --scanner-protocol-fixture`. This exercises hosted PostgreSQL and Supabase using temporary fixtures, including scan failures and cleanup. The loopback scanner fixture tests the API's ClamD protocol and failure handling; it does not run an antivirus engine or establish that production scanning is active. A production host still needs a real ClamAV daemon, updated signatures, and an installed cleanup schedule. Add `--email=YOUR_APPROVED_TEST_MAILBOX` only when live Resend tests are authorized, or select individual checks with `--only=storage,cleanup`. Use `--only=auth --email-fixture` to check authentication against PostgreSQL with captured emails when delivery is unavailable; this does not verify Resend.

See [the storage deployment files](../deployment/storage/README.md) for the private scanner and six-hour cleanup worker. They are preparation files until deployed and checked on the selected production host. Cleanup preserves finalized objects; uncertain PostgreSQL/Supabase commit outcomes need manual reconciliation against the actual records.

Supabase's [signed upload URL](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl), [signed download URL](https://supabase.com/docs/reference/javascript/file-buckets-createsignedurl), and [private bucket](https://supabase.com/docs/guides/storage/buckets/fundamentals) documentation describe the underlying Storage behavior.
